## 概要

インターフェースは，「何ができるか（契約）」を具体的な実装から切り離して宣言する仕組み．呼び出し側が具象型ではなく契約に依存できるため，実装の差し替えやテストダブルの注入が容易になり，[[疎結合]]な設計を実現できる．同じ目的に対して，Java/C# の `interface`，Go の暗黙的インターフェース，[[Rust]] の `trait`，Python の `Protocol` / ABC など，言語ごとに異なるアプローチが取られている．

## 詳細

### 公称型 vs 構造的型

インターフェースの「満たし方」には，大きく2つの型システム上の立場がある．

| 観点 | 公称的部分型（nominal） | 構造的部分型（structural） |
|------|------------------------|---------------------------|
| 判定基準 | 「実装する」と明示的に宣言したか | 必要なメソッド・シグネチャを持つか |
| 宣言の要否 | 必要（`implements` など） | 不要 |
| 代表例 | Java，C#，[[Rust]] の trait | Go，TypeScript，Python の `Protocol` |
| 利点 | 意図が明示される．IDE で実装一覧を辿れる | 既存型を後から適合させられる．ライブラリ間が疎結合になる |
| 欠点 | 実装時にインターフェースを import する必要があり結合が生じる | 意図しない適合が起こりうる．実装者を機械的に列挙しにくい |

Go では「インターフェースは実装側ではなく**利用側**で定義する」のが定石とされ，構造的型付けの利点を活かして，パッケージ間の依存を減らす設計が推奨される．

### 言語別の実装比較

| 言語・機構 | 型付け | 実装の宣言 | デフォルト実装 | ディスパッチ |
|------------|--------|------------|----------------|--------------|
| Java / C# `interface` | 公称 | `implements` が必要 | 可（Java 8 以降の default メソッド） | 動的（vtable） |
| Go `interface` | 構造 | 不要（暗黙） | 不可 | 動的（itab） |
| [[Rust]] `trait` | 公称 | `impl Trait for Type` が必要 | 可 | 静的・動的を選択可 |
| Python `Protocol` | 構造 | 不要（暗黙） | 可（既定実装を書ける） | 実行時はダックタイピング |
| Python ABC | 公称 | 継承または `register()` | 可 | 実行時はダックタイピング |
| TypeScript `interface` | 構造 | 不要（暗黙） | 不可（型のみ） | 実行時に型は消える |

### Rust の trait

`trait` は「共通の振る舞いを定義する」点で interface に似るが，いくつか本質的な違いがある．

```rust
trait Greeter {
    fn name(&self) -> String;
    // デフォルト実装を持てる
    fn greet(&self) -> String {
        format!("Hello, {}!", self.name())
    }
}

struct Cat;
impl Greeter for Cat {
    fn name(&self) -> String { "cat".to_string() }
}

// 静的ディスパッチ（単相化されゼロコスト）
fn greet_static<T: Greeter>(g: &T) -> String { g.greet() }

// 動的ディスパッチ（vtable 経由）
fn greet_dynamic(g: &dyn Greeter) -> String { g.greet() }
```

- **ディスパッチを選べる**: ジェネリクスや `impl Trait` による静的ディスパッチは単相化されるためゼロコスト抽象化になり，`dyn Trait` による動的ディスパッチは異種コレクションや実行時に型が決まる場面で使う．既定は静的ディスパッチを選び，必要な場合のみ `dyn` を使うのが定石
- **後付けで実装できる**: 型の定義を変更せずに `impl Trait for Type` を書けるため，標準ライブラリや外部クレートの型に自作トレイトを実装できる．Java の `implements` のように型の定義時点で宣言する必要がない
- **孤児ルール（orphan rule）**: ただしトレイトか型のどちらかが自クレートに属している必要がある．外部の型に外部のトレイトを実装したい場合は newtype パターンで包む
- **関連型・トレイト境界**: `type Item;` のような関連型や `where` 句によるトレイト境界で，interface より表現力の高い抽象化ができる
- 起源は [[Haskell]] の**型クラス**にあり，「型に対して後から振る舞いを追加する」という発想を受け継いでいる
- **2026年時点の状況**: トレイト内の `async fn`（ネイティブ非同期トレイト）が安定化済み．また従来「オブジェクト安全性（object safety）」と呼ばれていた性質は「dyn 互換性（dyn compatibility）」という名称に整理されている

### Python の Protocol

PEP 544（Python 3.8 で導入）による `typing.Protocol` は，**構造的部分型（静的ダックタイピング）**を型チェッカに認識させる仕組み．

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Greeter(Protocol):
    def greet(self) -> str: ...

class Cat:  # Greeter を継承していない
    def greet(self) -> str:
        return "meow"

def call(g: Greeter) -> str:
    return g.greet()

call(Cat())              # 型チェックを通る（構造が一致するため）
isinstance(Cat(), Greeter)  # runtime_checkable があれば True
```

| 観点 | ABC（抽象基底クラス） | Protocol |
|------|----------------------|----------|
| 型付け | 公称（継承または `register()` が必要） | 構造（メソッドが一致すれば満たす） |
| 既存クラスへの適用 | 変更または登録が必要 | 不要 |
| 実行時チェック | `isinstance()` が使える | `@runtime_checkable` を付ければ可（メソッドの**存在**のみ確認し，シグネチャは検証しない） |
| 主な用途 | 明示的な継承階層を作りたい場合 | サードパーティ型・レガシーコードへの型付け，ダックタイピングの静的検証 |

Python が本来持つダックタイピングの慣習を壊さずに静的型検査を導入できるのが `Protocol` の要点で，PEP 544 も ABC による公称型を置き換えるものではなく，両者は併存する立場を取っている．

### 設計原則

- **実装ではなくインターフェースに対してプログラムする**: GoF の原則．具象クラスへの依存を避け，差し替え可能性を確保する
- **依存性逆転の原則（DIP）**: 上位・下位モジュールの双方が抽象に依存するようにし，依存の向きを制御する
- **インターフェース分離の原則（ISP）**: 利用者に不要なメソッドへの依存を強制しない．インターフェースは小さく保つ（Go の `io.Reader` のようにメソッド1つが理想形）
- **過剰抽象化に注意**: 実装が1つしかないのに機械的にインターフェースを作ると，間接層が増えるだけで可読性を損なう

## ポイント

- インターフェースの本質は「実装と分離された**契約**」であり，[[疎結合]]・差し替え可能性・テスト容易性の基盤になる
- 公称型（Java・C#・Rust）は意図が明示される一方，構造的型（Go・TypeScript・Python の Protocol）は既存の型を後から適合させられる
- [[Rust]] の `trait` は静的・動的ディスパッチを選べ，外部の型にも後付けで実装できる点が interface と大きく異なる（起源は [[Haskell]] の型クラス）
- Python の `Protocol` は PEP 544 による構造的部分型で，ダックタイピングの慣習を保ったまま静的型検査を可能にする．ABC は公称型で用途が異なる
- 実装が1つしかない場面での機械的なインターフェース化は過剰抽象化になりやすい
