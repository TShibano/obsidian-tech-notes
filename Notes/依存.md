## 概要

依存（dependency）とは，あるコードが動作するために必要とする他のオブジェクト・モジュール・外部システムのことである．[[単体テスト]]では，依存を「共有 / プライベート」「可変 / 不変」「プロセス内 / プロセス外」「揮発性」などの軸で分類し，どの依存をテストダブルに置き換えるべきかを判断する．本ノートは主に Vladimir Khorikov『Unit Testing Principles, Practices, and Patterns』（邦訳『単体テストの考え方/使い方』）の分類に沿って整理する．

## 詳細

### 分類の軸

| 軸 | 種類 | 定義 | 例 |
|----|------|------|-----|
| 共有 | **共有依存**（shared） | テスト間で共有され，あるテストが別のテストの結果に影響を与えうる依存 | 静的な可変フィールド，データベース |
| | **プライベート依存**（private） | 共有されない依存．テストごとに新しいインスタンスを作れる | テスト内で生成するオブジェクト |
| 可変性 | **可変依存**（mutable） | 状態を変更できる依存．Khorikov は「協力者オブジェクト（collaborator）」と呼ぶ | エンティティ，リポジトリ |
| | **不変依存**（immutable） | 状態を変更できない依存．「値（value）」や値オブジェクト | 数値，文字列，値オブジェクト，列挙型 |
| 実行場所 | **プロセス外依存**（out-of-process） | アプリケーションの実行プロセスの外で動く依存．まだメモリ上にないデータへのプロキシ | データベース，外部 API，メッセージバス，ファイルシステム |
| | プロセス内依存（in-process） | 同じプロセス内のメモリ上にある依存 | 通常のクラス |
| 揮発性 | **揮発性依存**（volatile） | 次のどちらかを満たす依存（Mark Seemann の定義） | 下記参照 |

揮発性依存の条件:

1. 開発者のマシンにデフォルトで入っていない実行環境の構築を必要とする（DB，外部 API など）
2. 非決定的な振る舞いをする（乱数生成器，現在時刻を返すクラスなど）

### 軸どうしの関係

- **共有依存はすべて可変**である．不変のものはテスト間で干渉できないため，「共有かつ不変」の依存は存在しない
- 可変依存がすべて共有とは限らない．テストごとに作り直せばプライベート依存になる
- プロセス外依存の多くは共有かつ可変だが，**読み取り専用 API のような不変なプロセス外依存**はテスト間で干渉しないので共有依存ではない
- 共有依存と揮発性依存は重なるが同じではない．DB は共有かつ揮発性だが，ファイルシステムは共有でも揮発性ではない（どのマシンにもある）

```
依存
├── プロセス内
│   ├── 不変（値）……………… プライベート
│   └── 可変（協力者）
│       ├── プライベート …… 通常のオブジェクト
│       └── 共有 …………… 静的可変フィールド（避けるべき）
└── プロセス外
    ├── 不変 ………………… 読み取り専用 API（プライベート扱い）
    └── 可変 ………………… DB・メッセージバス（共有）
```

### 古典派とロンドン派での扱いの違い

| 学派 | テストダブルに置き換える対象 |
|------|------------------------------|
| ロンドン派（モック派） | 不変依存以外のすべて（可変依存全般） |
| 古典派（デトロイト派） | 共有依存のみ（テスト同士を隔離するため） |

古典派の考える「隔離」はテスト対象のクラス同士ではなく**テストケース同士**の隔離であり，そのために置き換えが必要なのは共有依存だけである．

### 管理下の依存と管理外の依存

Khorikov は統合テストの文脈で，プロセス外依存をさらに2つに分ける．

| 種類 | 定義 | 例 | モックすべきか |
|------|------|-----|---------------|
| **管理下の依存**（managed） | 自分のアプリケーションだけがアクセスし，外部から観察できない依存 | アプリ専用のデータベース | しない．実物を使う（実装の詳細なので） |
| **管理外の依存**（unmanaged） | 他のシステムからも観察できる依存 | SMTP サーバー，メッセージバス，外部 API | する．外部との契約（後方互換性）を検証する |

管理下の DB に対する呼び出しは実装の詳細なので，モックで検証するとリファクタリング耐性が落ちる．一方，管理外の依存へのメッセージは外部から見える振る舞いの一部なので，モックで検証する価値がある．

### 明示的な依存と暗黙的な依存

- **明示的な依存**: コンストラクタや引数で渡す依存．差し替えやすい
- **暗黙的な依存**: `DateTime.Now` や静的フィールドのように内部で直接参照する依存．テストで制御しにくい

不変なプロセス内依存（定数，列挙型）以外は，明示的な依存にするのが原則．

## ポイント

- 共有依存はすべて可変．共有かつ不変な依存は存在しない
- プロセス外依存でも不変なら共有依存ではない（読み取り専用 API など）
- 揮発性依存 = 環境構築が必要 or 非決定的．共有依存とは重なるが別の概念
- 古典派は共有依存だけを置き換え，ロンドン派は可変依存をすべて置き換える
- 統合テストでは管理下の依存は実物，管理外の依存はモックにする
- 暗黙的な依存（現在時刻，静的状態）は明示的な依存に変えるとテストしやすい
- 依存をインフラ層に集めると，[[ドメインモデル]]がモックなしでテストできる
