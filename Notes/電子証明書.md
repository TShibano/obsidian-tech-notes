## 概要

電子証明書（デジタル証明書）は，公開鍵とその持ち主（人・組織・機器・ドメインなど）の結び付きを，信頼された第三者である認証局（CA）の電子署名で保証するデータである．X.509 形式が事実上の標準で，TLS，S/MIME，コード署名，文書署名，クライアント認証，電子政府（マイナンバーカード）など幅広く使われる．本ノートは証明書全般と PKI の階層構造に重点を置き，TLS サーバ向けの詳細（DV/OV/EV，ACME，CT など）は [[TLSサーバ証明書]] を参照する．

## 詳細

### 証明書の種類と役割

| 種類 | 役割 | 特徴 |
|---|---|---|
| ルート証明書（ルート CA 証明書） | 信頼の起点（トラストアンカー） | 自己署名．トラストストアに事前収録される．秘密鍵はオフライン保管が定石 |
| 中間証明書（中間 CA / 下位 CA 証明書） | ルートに代わって日常の発行を担う | ルートまたは別の中間 CA が署名．漏えい時の影響範囲が局所化でき，失効もその枝に限定される |
| エンドエンティティ証明書（リーフ） | 実際に通信・署名する主体の証明書 | サーバ，クライアント，コード署名，S/MIME など．CA としては使えない |
| クロス証明書 | 別のルートから発行された CA 証明書で，新ルート未配布のクライアントでもチェーンを成立させる | ルート移行期に使う（既存知識） |
| 自己署名証明書 | 発行者と所有者が同一 | ルート証明書も技術的には自己署名．通常の自己署名リーフは開発・閉域用途 |

「CA 証明書」はルートと中間の総称で，リーフとの違いは basicConstraints の cA が真であり，keyUsage に keyCertSign を持つ点にある．RFC 5280 は「keyCertSign ビットは，主体の公開鍵が公開鍵証明書上の署名検証に使われる場合に立てる」とし，立てる場合は basicConstraints の cA も真でなければならないとする．

### 証明書チェーン（証明書パス）の検証

クライアントはリーフから順に，各証明書の署名を発行者の公開鍵で検証し，トラストストアにあるトラストアンカーまで到達できれば信頼する．各段で有効期間，失効状態，制約（後述）も確認する．サーバは通常，リーフと中間 CA を送り，ルートは送らない（クライアントが既に持つため）．中間の送り忘れは一部クライアントで検証エラーになる．

```
ルート CA（自己署名・オフライン）
 └─ 中間 CA（policy / issuing）
     └─ リーフ（サーバ・クライアント・署名用など）
```

### X.509 v3 の構造と CA 向け拡張

基本フィールド（version，serialNumber，issuer，validity，subject，subjectPublicKeyInfo，extensions）と署名は [[TLSサーバ証明書]] に記載があるため省略する．ここでは PKI の階層制御に関わる拡張に絞る．

- basicConstraints: cA 真偽値で，証明書の公開鍵が「証明書の署名検証に使えるか」を示す．pathLenConstraint は cA が真のときのみ意味を持ち，配下に許す中間 CA の段数を制限する（RFC 5280 4.2.1.9）．
- keyUsage / extendedKeyUsage: 鍵の用途（keyCertSign，digitalSignature，serverAuth，clientAuth，codeSigning，emailProtection など）を制限する．
- nameConstraints: CA 証明書にのみ使え，配下の証明書の主体名（DN と SAN）が入るべき名前空間を制限する（RFC 5280 4.2.1.10）．私設 CA で「自社ドメイン以外は発行させない」ために使える．
- authorityKeyIdentifier / subjectKeyIdentifier: チェーン構築時の鍵の対応付けに使う．
- CRL Distribution Points / Authority Information Access: CRL の取得先，OCSP レスポンダ，発行者証明書の取得先を示す．

### トラストストア（ルートストア）

トラストストアは「公に信頼するルート」の集合で，運営者ごとに独自のルートプログラムがある．

| 運営者 | ストア / プログラム | 備考 |
|---|---|---|
| Google | Chrome Root Store | Chrome は Windows・macOS で 108，Linux・ChromeOS で 114，Android で 115 以降に独自ストアを使用（二次情報）．iOS は対象外 |
| Mozilla | Mozilla Root Store | Firefox，Thunderbird，多くの Linux ディストリビューションの CA バンドルの元 |
| Apple | Apple Root Certificate Program | macOS，iOS，Safari |
| Microsoft | Microsoft Trusted Root Program | Windows，Edge．OS の証明書ストアで管理 |

- 各プログラムは CCADB（Common CA Database）を通じて CA の情報を共有する．
- CA が違反を起こすとルートが除外（ディストラスト）されうる．例として SwissSign Gold CA - G2 は 2026-04-15 付で Chrome と Mozilla から除外されたが，Apple は継続して信頼しているとされる（二次情報のみで一次情報は未確認）．ストアにより信頼が食い違う場合がある．
- Chrome Root Program Policy v1.8（2026-02-05 更新）は，鍵生成から15年を超えたルートを継続的に除外する方針で，下位 CA の最大有効期間は3年を推奨している．
- 同ポリシーは公開 TLS の階層を専用化する．2026-06-15 以降に開示される下位 CA は serverAuth のみ，2027-03-15 以降に発行されるサブスクライバ証明書も serverAuth のみとする．公開 CA の証明書でクライアント認証はできなくなる流れである．
- 企業や組織は自前のルートをストアに追加（MDM，グループポリシー，`update-ca-certificates` など）して私設 CA を信頼させる．アプリによっては OS ストアでなく独自のバンドルを使う（Java の cacerts，Python の certifi，Firefox の旧来設定など．既存知識）．

### 失効（CRL / OCSP）

- CRL（Certificate Revocation List）: CA が署名した，失効済み証明書のタイムスタンプ付き一覧（RFC 5280）．取得先は証明書の CRL Distribution Points に入る．リストが大きくなりやすいため，パーティション化や，ブラウザ側で圧縮して配布する方式（CRLite など）が使われる．
- OCSP（RFC 6960）: 個別証明書の状態をオンラインで問い合わせる．プライバシーと可用性の課題があり，OCSP stapling で緩和できる．
- 近年の流れは OCSP 縮小と CRL・短命証明書への移行である．CA/Browser Forum は 2023 年のバロット SC-063v4 で OCSP を任意にし CRL を必須にし，Let's Encrypt は 2025-08-06 に OCSP を停止した．詳細は [[TLSサーバ証明書]] を参照．
- 中間 CA の失効は配下すべてに影響するため，階層設計時に失効の運用手順を決めておく．

### 自己署名証明書とプライベート CA

- 自己署名証明書: 発行者と主体が同じ．ルート CA 証明書は定義上これだが，ここでは単体で使うサーバ証明書を指す．信頼を得るには個別に端末へ登録する必要があり，台数が増えると管理が破綻する．
- プライベート CA（私設 CA / 社内 PKI）: 組織が自前で運用する CA．内部サービス，mTLS，機器認証（IoT，VPN，Wi-Fi の 802.1X），サービスメッシュなどで使う．
- 設計の定石:
  - ルートはオフラインに置き，中間 CA にだけ発行させる（ルートは中間 CA の署名・再認証のときだけ起動する）．
  - 小規模なら「ルート + 発行 CA」の2階層から始め，大規模になって構造的な制約が要るときに policy CA 層を足す．
  - 秘密鍵は HSM やエアギャップ環境で生成・保管する．
  - 名前制約と pathLenConstraint で，配下の発行範囲を絞る．
  - 配布するルートは有効期間を長めに，発行証明書は短寿命にして自動更新する．
- 代表的な実装・サービス: Active Directory 証明書サービス（[[Active Directory]]），AWS Private CA，Smallstep の step-ca，HashiCorp Vault の PKI シークレットエンジン，cert-manager（[[Kubernetes]]）など．
- 公開 CA がクライアント認証から退く流れ（上記 serverAuth 専用化）により，mTLS には私設 CA を使うのがいっそう標準になる．

### 用途別の証明書

- TLS サーバ証明書: [[TLSサーバ証明書]] を参照．
- TLS クライアント証明書: mTLS，VPN，Wi-Fi 認証などで端末・ユーザを識別する．
- S/MIME 証明書: メールの署名・暗号化．
- コード署名証明書: ソフトウェアの配布元と改ざんなしを示す．
- 文書署名・タイムスタンプ: 長期署名（PAdES など）で用いる（既存知識）．
- 日本の公的個人認証: マイナンバーカード等の IC カードに「署名用電子証明書」と「利用者証明用電子証明書」の2種類が入る．署名用は電子文書の作成・送信時に，利用者証明用はマイナポータルなどへのログイン時に使う．個人向けの有効期間は発行日から5回目の誕生日まで（二次情報）．民間事業者は主務大臣の認定を受けて利用できる．

### 最新動向（2026-11-09 時点）

- 有効期間の短縮: SC-081v3 により公開 TLS 証明書の最大有効期間は 2026-03-15 に200日，2027-03-15 に100日，2029-03-15 に47日と段階的に短縮される．現在の上限は200日．更新の自動化（ACME）が前提になる．詳細は [[TLSサーバ証明書]]．
- 用途の専用化: 上記の Chrome Root Program Policy により，公開 PKI は TLS サーバ認証専用になる．
- ポスト量子対応: Chrome は 2026-02-27 の発表で，従来の X.509 に PQC を載せた証明書を Chrome Root Store に入れる計画は当面なく，Merkle Tree Certificates（MTC）を公開 Web 証明書の量子耐性への道筋とした．CA が1つのツリーヘッドに署名し，ブラウザに送る証明書は包含証明という軽量なものになる．フェーズ2（CT ログ運営者の招待）は2027年第1四半期，フェーズ3（MTC 専用の Quantum-resistant Root Store）は2027年第3四半期が目標である．Chrome の計画は Google 公式ブログで確認できる．Let's Encrypt も 2026-06-05 に MTC を採用する方針を示し，2026年末にステージング，2027年に本番を目指すと報じられている（Let's Encrypt 側の一次情報は未確認）．計画は変わりうる．
- 階層面では，ルートの鍵年齢（15年）による定期入れ替えと，下位 CA の短寿命化が進み，ルート移行時にクロス署名やトラストストア更新への対応が運用課題になる．

## ポイント

- 電子証明書は「公開鍵と主体の結び付き」を CA の署名で保証する．形式は X.509 v3（RFC 5280）．
- 信頼はチェーンとトラストアンカー（トラストストアのルート）で成立する．サーバはリーフと中間を送る．
- ルートはオフライン，発行は中間 CA，という分離が基本．漏えい時の影響を局所化できる．
- ルート・中間とリーフの違いは basicConstraints の cA と keyUsage の keyCertSign．nameConstraints と pathLenConstraint で配下を制御できる．
- トラストストアは OS・ブラウザごとに異なり，ルート除外の結果が食い違うことがある．
- 失効は CRL と OCSP．OCSP は縮小し，CRL と短命証明書に重心が移っている．
- 内部用途・mTLS は私設 CA．公開 CA は serverAuth 専用化に向かう．
- 有効期間は 200日 → 100日 → 47日と短縮．PQC は Merkle Tree Certificates が有力な道筋．
