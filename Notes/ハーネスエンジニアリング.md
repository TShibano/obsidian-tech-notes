## 概要

ハーネスエンジニアリングは，AI エージェントの周囲にある「モデル以外のすべて」——ツール，コンテキスト，権限，テスト，リンター，観測性，検証ループなど——を設計・構築する技術領域である．「Agent = Model + Harness」という捉え方に基づき，モデルの能力を信頼できる振る舞いに変えるのはハーネスの仕事だと考える．2026年2月の OpenAI の記事をきっかけに広まり，プロンプトエンジニアリング，コンテキストエンジニアリングに続く段階として注目されている．

## 詳細

### 背景：OpenAI の実験

OpenAI の Ryan Lopopolo は2026年2月の記事「Harness engineering: leveraging Codex in an agent-first world」で，約5か月間の社内実験を報告した．

- 3人のエンジニアが，**人間が1行もコードを書かずに**約100万行規模のプロダクト（ベータ版）を開発
- 約1,500件の PR を Codex エージェントが作成・レビューし，多くはエージェントがマージ
- 人間の仕事は「コードを書くこと」ではなく，**エージェントが信頼できるコードを生成できる環境を設計すること**になった

主な工夫:

| 工夫 | 内容 |
|------|------|
| 地図としての AGENTS.md | 巨大な指示書ではなく，構造化された `docs/` への目次として短く保つ |
| 厳格なレイヤー構造 | ドメインごとに固定のレイヤーと依存方向を定め，カスタムリンターと構造テストで CI 上で機械的に強制 |
| エージェントが読める環境 | ログ・メトリクス・UI をエージェント自身が参照し，自分で検証できるようにする |
| エントロピー管理 | ドキュメントの陳腐化やパターンの劣化を定期的なエージェント作業で掃除する（ガベージコレクション） |

### Böckeler による整理：Guides と Sensors

Thoughtworks の Birgitta Böckeler は martinfowler.com の記事（2026年2月にメモ，4月に拡充）で，コーディングエージェント利用者側のハーネスを制御システムとして整理した．

| 分類 | 役割 | 例 |
|------|------|-----|
| **Guides**（フィードフォワード） | 行動前に方向づけ，良い結果の確率を上げる | CLAUDE.md / AGENTS.md，[[エージェントスキル]]，設計ドキュメント |
| **Sensors**（フィードバック） | 行動後に観察し，自己修正させる | テスト，リンター，型チェック，AI レビュー |

フィードフォワードだけではルールが守られたか検証できず，フィードバックだけでは同じ失敗を繰り返す．両方が必要．

実行方式の軸:

- **Computational（計算的）**: 決定論的で高速．テスト，リンター，型チェッカー，構造テスト
- **Inferential（推論的）**: LLM による意味的な判断．非決定論的だが表現力が高い（AI レビュー，LLM-as-judge）

規制対象の軸:

1. **Maintainability harness**: コード品質・保守性（既存ツールが豊富）
2. **Architecture fitness harness**: 性能要件，観測性などのアーキテクチャ特性
3. **Behaviour harness**: 機能的な正しさ．最も難しく，AI 生成テストに頼りすぎる問題がある

人間の開発者は社会的責任感や組織の記憶といった「暗黙のハーネス」を持っているが，エージェントは持たない．ハーネスはそうした人間の専門知識を外部化する試みでもある．

### 長時間エージェントのハーネス（Anthropic）

Anthropic は2025年11月の記事で，複数のコンテキストウィンドウにまたがる長時間タスク向けのハーネスを紹介した．

- **Initializer agent**: 最初のセッションで `init.sh`，進捗ファイル，機能リスト（JSON，すべて「未達成」から開始），初期 git コミットを作る
- **Coding agent**: 以降のセッションで「1回に1機能」だけ実装し，終わるたびに git コミットと進捗ファイルを更新
- 各セッションの最初に `pwd` → git log と進捗ファイルの確認 → 次の未完了機能の選択，という手順を踏む
- E2E テスト（ブラウザ自動化）で機能の完了を検証する

### ハーネスの構成要素

| レイヤー | 内容 | Claude Code での例 |
|----------|------|---------------------|
| コンテキスト・メモリ | 指示書，ドキュメント，進捗記録 | CLAUDE.md，メモリ |
| ツール | エージェントが使える操作 | 組み込みツール，[[MCP]] サーバー |
| 権限・ガードレール | 危険な操作の制限，承認 | permission mode，hooks |
| 検証ループ | 結果の自動チェック | テスト，リンター，hooks での自動実行 |
| オーケストレーション | タスク分割・委譲 | [[サブエージェント]]，[[エージェントスキル]] |
| 観測性 | 何が起きたかの追跡 | ログ，トレース |

### 他のエンジニアリングとの違い

| 段階 | 対象 | 問い |
|------|------|------|
| プロンプトエンジニアリング | 1回の指示文 | どう頼むか |
| コンテキストエンジニアリング | モデルに渡す情報全体 | 何を見せるか |
| ハーネスエンジニアリング | 実行環境・制御系全体 | どう制約し，どう検証するか |

信頼性に関わるロジック（リトライ，ルーティング，検証，メモリ，制御フロー）はプロンプトの中に隠さず，システム側の明示的で検査可能な部品にする，というのが基本姿勢である．ルーティングやガードレールの判定には，テキストを生成せず型付きの判定だけを返す [[Jev]] や [[Nimble]] のような判定モデルを使う例も出てきている．

## ポイント

- Agent = Model + Harness．モデル以外のすべてがハーネス
- 人間の役割は「コードを書く」から「エージェントが正しく動ける環境を作る」へ移る
- Guides（事前の方向づけ）と Sensors（事後の検証）を組み合わせる
- 決定論的なチェック（テスト・リンター・構造テスト）で制約を機械的に強制するのが効く
- 長時間タスクでは進捗ファイル・機能リスト・git でセッション間の状態を引き継ぐ
- AGENTS.md / CLAUDE.md は短い目次にとどめ，詳細はリポジトリ内のドキュメントに置く
- 振る舞いの正しさの検証（Behaviour harness）はまだ難しい
