## 概要

ドメインモデルは，ソフトウェアが扱う業務領域（ドメイン）の概念・ルール・振る舞いを表現したモデルである．Martin Fowler は『Patterns of Enterprise Application Architecture』（2003）で「振る舞いとデータの両方を組み込んだドメインのオブジェクトモデル」と定義し，複雑なビジネスロジックを整理するためのパターンとして位置づけた．

## 詳細

### 2つの意味

「ドメインモデル」という言葉は文脈によって指すものが少し異なる．

| 文脈 | 意味 |
|------|------|
| 概念モデル（分析） | 業務の概念とその関係を図や言葉で表したもの．実装技術に依存しない |
| 実装パターン（PoEAA） | 業務ルールをエンティティ・値オブジェクトなどのオブジェクト群として実装したコード |
| [[ドメイン駆動設計]] | 上記2つを一致させることを目指す．ユビキタス言語でモデルとコードを結びつける |

### Transaction Script との比較

Fowler はビジネスロジックの組織化パターンとして，Transaction Script / Table Module / Domain Model の3つを挙げている．

| 観点 | Transaction Script | Domain Model |
|------|--------------------|--------------|
| ロジックの置き場所 | 処理（ユースケース）ごとの手続き | データを持つオブジェクト自身 |
| 向いている規模 | 単純な CRUD 中心の業務 | ルールが多く分岐が複雑な業務 |
| 初期コスト | 低い | 高い（モデリングが必要） |
| 複雑化への耐性 | 重複・分岐が増えて崩れやすい | 振る舞いが凝集し変更に強い |

### 貧血ドメインモデル（Anemic Domain Model）

ドメインオブジェクトが getter/setter だけを持ち，ロジックがすべてサービス層に置かれている状態を Fowler は**アンチパターン**と呼んだ．見た目はドメインモデルだが実態は Transaction Script であり，データと処理を一緒にするというオブジェクト指向の基本から外れている．

対になるのが**リッチドメインモデル**で，不変条件の検証や状態遷移をオブジェクト自身が担う．

```python
# 貧血モデル：ルールが外にある
class Order:
    def __init__(self):
        self.status = "draft"
        self.lines = []

def confirm(order):  # サービス層
    if not order.lines:
        raise ValueError("明細がない")
    order.status = "confirmed"

# リッチモデル：ルールがオブジェクト内にある
class Order:
    def __init__(self):
        self._status = "draft"
        self._lines = []

    def confirm(self):
        if not self._lines:
            raise ValueError("明細がない")
        self._status = "confirmed"
```

なお，関数型スタイルでは「不変データ + 純粋関数」でドメインを表現するため，データと関数が分かれていても貧血モデルの問題（不変条件の散逸）にはならない．問題はデータと処理の分離そのものより，**ルールがどこにあるか分からなくなること**にある．

### 戦術的 DDD の構成要素

| 要素 | 役割 |
|------|------|
| エンティティ | 識別子で区別される，ライフサイクルを持つオブジェクト |
| 値オブジェクト | 属性の値で等価性が決まる不変オブジェクト |
| 集約 | 不変条件を守る整合性の境界．外部からは集約ルート経由でのみ操作する |
| ドメインサービス | 特定のエンティティに属さないドメインロジック |
| ドメインイベント | ドメインで起きた重要な出来事 |

### テストの観点から見たドメインモデル

Vladimir Khorikov『Unit Testing Principles, Practices, and Patterns』（邦訳『単体テストの考え方/使い方』）は，コードを「ドメインにとっての重要性・複雑さ」と「協力者オブジェクトの数」の2軸で4象限に分類する．

| | 協力者が少ない | 協力者が多い |
|---|---|---|
| **複雑・重要** | ドメインモデル / アルゴリズム（単体テストの費用対効果が最大） | 過度に複雑なコード（分割すべき） |
| **単純** | 取るに足らないコード（テスト不要） | コントローラ（統合テストで確認） |

ドメインモデルを**プロセス外[[依存]]から切り離し**，外部とのやり取りはアプリケーションサービス（コントローラ）に寄せることで，ドメインモデルはモックなしで高速にテストできるようになる．これは [[Functional Core, Imperative Shell]] やヘキサゴナルアーキテクチャと同じ発想である．

## ポイント

- ドメインモデルは「データ + 振る舞い」で業務ルールを表現する．業務が複雑なほど効果が大きい
- 単純な CRUD なら Transaction Script のほうが安上がり．規模に応じて選ぶ
- getter/setter だけのモデルは貧血ドメインモデル．ルールが散らばり不変条件が守られにくい
- ドメインモデルはプロセス外依存を持たせないのが原則．そうすると単体テストの価値が最も高い領域になる
- [[ドメイン駆動設計]] は，概念モデルと実装モデルを一致させる設計手法
