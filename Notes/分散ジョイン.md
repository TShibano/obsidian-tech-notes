## 概要

分散ジョイン（Distributed Join）とは，[[超並列プロセシング]]（MPP）や[[Apache Spark]]のような分散処理エンジンにおいて，複数ノードに分散配置されたデータセット同士を結合する処理のこと．単一マシンのジョインと異なり，結合キーが異なるノードに存在するため，データをネットワーク越しに再配置（シャッフル）する必要があり，これが分散ジョインの性能上の最大の課題になる．

## 詳細

### なぜ分散が難しいのか

ジョインは本質的に「同じキーを持つ行を同じ場所に集める」処理．単一ノードならメモリ内で完結するが，分散環境ではデータが複数ノードに散らばっているため，以下のいずれかの方法でキーを揃える必要がある:

1. 小さい方のテーブルを全ノードに複製する（ブロードキャスト）
2. 両方のテーブルを同じキーで再パーティショニングする（シャッフル）

### ブロードキャストジョイン（Broadcast Hash Join）

一方のテーブルが十分小さい（メモリに収まる）場合，そのテーブルをクラスタ内の全ワーカーに複製し，各ワーカーがローカルでハッシュ結合を行う方式．

| 項目 | 内容 |
|------|------|
| **前提条件** | 片方のテーブルが閾値以下（Spark のデフォルトは 10MB，`spark.sql.autoBroadcastJoinThreshold` で変更可） |
| **メリット** | ネットワークシャッフルが発生せず高速．大テーブル側の再分散が不要 |
| **デメリット** | 小テーブルが大きすぎるとメモリ不足（OOM）を招く |
| **典型例** | ファクトテーブル（大）とディメンションテーブル（小）の結合（スタースキーマ） |

### シャッフルハッシュジョイン（Shuffle Hash Join）

両方のテーブルを結合キーのハッシュ値でパーティショニングし直し（シャッフル），同じキーが同じパーティション/タスクに集まるようにしてからローカルでハッシュ結合する方式．

| 項目 | 内容 |
|------|------|
| **前提条件** | どちらのテーブルもブロードキャストできないほど大きい |
| **メリット** | 大テーブル同士でも結合可能 |
| **デメリット** | 両テーブルのシャッフル（ネットワーク I/O・ディスク I/O）が発生し高コスト．片方のパーティションが均等でないとデータスキューが起きやすい |
| **関連戦略** | ソートマージジョイン（Sort Merge Join）は，シャッフル後に両側をソートしてマージする方式で，メモリ効率が良く大規模結合の既定戦略になっていることが多い（Spark 等） |

### 戦略選択の基準（Spark を例に）

```
テーブルサイズを見積もる
  ├─ 片方が閾値以下 → Broadcast Hash Join
  ├─ 両方大きい・キーが一意/低カーディナリティでない → Sort Merge Join（既定）
  └─ 明示的にヒントを指定 → Shuffle Hash Join 等を強制可能
```

[[Apache Spark]] では `EXPLAIN` で実際に選ばれた結合戦略を確認でき，`/*+ BROADCAST(t) */` のような結合ヒントで戦略を明示的に指定することも可能．

### データスキューへの対策

シャッフルハッシュジョイン・ソートマージジョインでは，特定キーにデータが偏る「データスキュー」が性能劣化の主要因になる．対策として，キーにソルト（乱数サフィックス）を付与して分散を均す，スキューキーを検出して別処理にする（Spark 3.0+ の Adaptive Query Execution によるスキュー結合最適化）などがある．

## ポイント

- 分散ジョインの本質は「同じキーを同じノードに集める」ためのデータ再配置コスト
- ブロードキャストジョインはシャッフル不要で高速だが，小テーブル限定
- シャッフルハッシュ／ソートマージジョインは大テーブル同士に対応するが，ネットワークコストが大きい
- データスキューは分散ジョインの典型的な性能ボトルネックで，ソルティングや AQE で緩和する
- [[クエリオプティマイザ]]がテーブル統計情報をもとに，どの結合戦略を採るかを自動選択する
