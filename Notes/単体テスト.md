## 概要

単体テスト（ユニットテスト）は，プログラムを構成する小さな単位（関数・メソッド・クラスなど）が期待どおりに動作するかを自動で検証するテスト．テストピラミッドの最下層を成し，高速かつ大量に実行できることから，リファクタリングや継続的インテグレーションにおける安全網として機能する．

## 詳細

### 「単位（unit）」の定義 — 2つの学派

「単体」が何を指すかは論争があり，代表的な2つの立場がある．

| 観点 | Detroit 派（古典派 / Classicist） | London 派（モック派 / Mockist） |
|------|-----------------------------------|--------------------------------|
| 単位の定義 | 観測可能な結果を生む「振る舞い」の単位（複数クラスの協調も含む） | 1クラス（時に1メソッド） |
| 隔離の対象 | テスト同士（並列実行できること） | テスト対象と協力オブジェクト |
| テストダブル | 主に管理外の依存（DB・外部API）にのみ使う | ほぼすべての依存に使う |
| 検証対象 | 最終的な状態・戻り値 | オブジェクト間の相互作用 |
| 進め方 | inside-out（内側から） | outside-in（外側から） |

Martin Fowler は同じ区別を **solitary（孤立）テスト**（すべての協力オブジェクトをテストダブルに置換）と **sociable（社交的）テスト**（実物の協力オブジェクトを使う）と呼んでいる．どちらか一方が正解ではなく，管理外の依存（外部システム）だけを置き換える折衷が実務では扱いやすい．

### テストダブルの5分類（Meszaros）

| 種類 | 役割 |
|------|------|
| **Dummy** | 引数を埋めるためだけの値．実際には使われない |
| **Stub** | 決められた値を返す．入力方向の依存を代替する |
| **Spy** | 呼び出された内容を記録する．検証は後から行う |
| **Mock** | 期待される呼び出しをあらかじめ設定し，相互作用を検証する |
| **Fake** | 軽量な実動作を持つ代替実装（インメモリ DB など） |

実務上の重要な区別は **Stub と Mock** にある．Stub は「テスト対象に値を供給する」ためのものなので，**Stub との相互作用を検証してはいけない**（実装の詳細に踏み込んだ過剰仕様なテストになる）．一方 Mock は「外部への副作用が正しく行われたか」を検証する目的で使う．

### AAA パターン

テストの構造は Arrange（準備）・Act（実行）・Assert（検証）の3ステップに揃えると読みやすくなる．BDD 系では Given-When-Then と呼ばれる．

- Act が複数行になる場合，APIの設計に問題がある可能性がある
- 1つのテストで検証する振る舞いは1つに絞る（Assert が増えるならテストを分ける）

### 良い単体テストの4本柱

Vladimir Khorikov『Unit Testing: Principles, Practices, and Patterns』は，価値ある単体テストの条件を4つに整理している．

| 柱 | 内容 |
|----|------|
| **退行に対する保護** | バグ（退行）を検出できる力．実行されるコードの量と複雑さに比例する |
| **リファクタリングへの耐性** | 挙動を変えないリファクタリングで失敗しない（偽陽性を出さない）こと |
| **迅速なフィードバック** | 実行が速く，開発の流れを止めないこと |
| **保守のしやすさ** | テスト自体が読みやすく，壊れにくいこと |

このうち「リファクタリングへの耐性」が最も軽視されやすい．実装の詳細ではなく**観測可能な振る舞い**をテストすることで確保でき，モックの多用はこれを損なう．

### テストピラミッド

下から順に，単体テスト（多数・高速）→ 結合テスト → E2E テスト（少数・低速）と積み上げる考え方．上位のテストほど実行が遅く，環境要因で不安定（flaky）になりやすいため，数を絞り，検証の主戦場を単体テストに置く．

### よくあるアンチパターン

- **カバレッジの目的化**: カバレッジは「テストされていない箇所」を見つける指標であり，高さ自体が品質を保証しない
- **private メソッドの直接テスト**: 実装の詳細に結合し，リファクタリング耐性を失う．公開された振る舞い経由で検証する
- **モックだらけのテスト**: 実装をそのまま写経したテストになり，退行を検出できなくなる
- **テスト間の状態共有**: 実行順序に依存して不安定になる．各テストは独立して実行できるようにする

### 設計との関係

テストが書きにくいコードは，設計に問題があるサインであることが多い．依存性注入で外部依存を差し替え可能にする，あるいは [[Functional Core, Imperative Shell]] のように純粋な計算部分を切り出すことで，テストダブルなしに検証できる範囲が広がる．[[テスト駆動開発]] はテストを先に書くことで，この分離を設計段階から強制する手法といえる．

## ポイント

- テストピラミッドの最下層を担い，**高速・大量・安定**であることが価値の源泉
- 「単体」の定義には Detroit 派（振る舞い単位）と London 派（クラス単位）があり，テストダブルの使用量が大きく異なる
- Stub は値の供給，Mock は副作用の検証と役割が異なり，**Stub との相互作用を検証しない**のが原則
- 実装の詳細ではなく観測可能な振る舞いをテストすることで，リファクタリングへの耐性が得られる
- テストしにくさは設計の問題であり，[[Functional Core, Imperative Shell]]のような分離が根本的な解決になる
