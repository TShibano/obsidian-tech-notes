## 概要

Functional Core, Imperative Shell（FCIS）は，Gary Bernhardt が2012年の講演「Boundaries」および Destroy All Software のスクリーンキャストで提唱したアーキテクチャパターン．アプリケーションを，純粋関数だけで構成される「関数型のコア（Functional Core）」と，I/O や副作用を担う薄い「命令型のシェル（Imperative Shell）」に分離する．[[関数型プログラミング]]の考え方を，言語を問わず設計指針として持ち込める点が特徴．

## 詳細

### 2つの層

| 観点 | Functional Core | Imperative Shell |
|------|-----------------|------------------|
| 責務 | ビジネスロジック・判断・計算 | I/O，DB アクセス，ネットワーク，時刻・乱数，UI |
| 純粋性 | 純粋関数のみ（副作用なし） | 副作用を持つ（不純） |
| 依存 | ほぼ持たない | 外部システムへの依存を集約 |
| 分岐（パス）の数 | 多い | 少ない（一本道に近い） |
| テスト方法 | 大量の高速な[[単体テスト]] | 少数の結合テスト |

Bernhardt の核心的な指摘は「**コアは分岐が多いが依存が少なく，シェルは依存が多いが分岐が少ない**」という非対称性にある．分岐の多い箇所（＝バグが潜む箇所）に依存がないため，テストダブルなしで網羅的に検証できる．

### なぜテストが楽になるか

純粋関数は「入力を与えて戻り値を検証する」だけでテストできるため，モックやスタブといったテストダブルが原理的に不要になる．一方シェルは分岐が少ないので，少数の結合テストで十分カバーできる．結果として，テストピラミッドが設計上自然に成立する．

### 実装の指針

- **ミューテーションを最後に隔離する**: 可能な限りミューテーションなしで処理を進め，状態変更を別の場所へ押し出す
- **「読む → 計算する → 書く」の順に構造化する**: 関数の途中で I/O せず，必要なデータを先に読み込んでからコアへ渡す
- **コアは値だけを受け取り，値だけを返す**: 時刻・乱数・設定なども引数として渡す（環境をコアに持ち込まない）
- **意思決定と実行を分ける**: コアが「次に何をすべきか」を表す値（コマンド・イベント）を返し，シェルがそれを解釈して実行すると，分離が徹底できる

### 類似アーキテクチャとの関係

| アーキテクチャ | 軸となる考え方 | FCIS との関係 |
|----------------|----------------|----------------|
| ヘキサゴナル（ポート＆アダプタ） | 依存の向きを内側へ | 境界の引き方は近いが，FCIS は「純粋性」を基準にする |
| クリーンアーキテクチャ | レイヤと依存性のルール | レイヤ数が多く重厚．FCIS はより軽量な指針 |
| [[ドメイン駆動設計]] | ドメインモデルを中心に置く | ドメイン層を純粋関数で書くと FCIS と一致する |

いずれも「ビジネスロジックを外部システムから守る」点で共通するが，FCIS は抽象化（インターフェース）ではなく**純粋性**で境界を引くため，依存性注入を多用せずに済むのが違い．

### 適用時の注意

- コアに渡すためのデータ変換コストが増える場合がある（特に巨大な状態を扱うとき）
- 大量データのコピーが発生しうるため，パフォーマンス要件とのトレードオフを見る必要がある
- 多くの言語は純粋性を強制できないため，レビューや静的解析による規律が必要
- 2025年10月には Google Testing Blog でも紹介されており，関数型言語に限らない一般的な設計指針として広がっている

## ポイント

- 純粋なコアと不純なシェルに分け，**副作用をアプリケーションの外縁に押し出す**パターン
- 「コアは分岐が多く依存が少ない，シェルは依存が多く分岐が少ない」という非対称性がテスト戦略の根拠
- テストダブルに頼らずに[[単体テスト]]を書けるようになり，テストの速度・安定性が大きく向上する
- ヘキサゴナルやクリーンアーキテクチャと目的は近いが，抽象化ではなく**純粋性**で境界を引く点が異なる
- 関数型言語専用の手法ではなく，TypeScript・Python・Java など手続き型・OOP 言語にも適用できる
