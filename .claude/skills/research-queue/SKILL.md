# Research Queue 処理

GitHub Issue に記載された調査項目を処理し，`Notes/` に技術ノートを作成します．
`Notes/` に同名のノートが既にある項目は，内容を確認して当日時点の最新情報に更新します．
調査は Sonnet 5.5 のサブエージェントが項目ごとに並列で行い，メインの Opus 5.5 が一次情報源と突き合わせて精査してから反映します．

項目ごとの処理モード:

| モード | 条件 | 内容 |
|--------|------|------|
| **新規** | `Notes/{トピック名}.md` が存在しない | 調査してノートを新規作成する |
| **更新** | `Notes/{トピック名}.md` が存在する | 既存ノートを読み，古くなった記述の修正と新情報の追記を行う |

## 使用方法

```
/research-queue [issue番号] [最大処理数]
```

- `issue番号`: 省略時は Issue #1 を使用
- `最大処理数`: 省略時は 3（コンテキスト制限を考慮）

**例:**
- `/research-queue` → Issue #1 から最大3件処理
- `/research-queue 1 5` → Issue #1 から最大5件処理
- `/research-queue 2` → Issue #2 から最大3件処理

## 処理手順

### 1. 引数の解析

`$ARGUMENTS` を解析して Issue 番号と最大処理数を取得:

- 第1引数: Issue 番号（省略時は 1）
- 第2引数: 最大処理数（省略時は 3）

**例:**
- `(空)` → Issue #1，最大3件
- `2` → Issue #2，最大3件
- `1 5` → Issue #1，最大5件

### 2. Issue の読み取り

`gh issue view <番号> --json body` コマンドで Issue 本文を取得する．

### 3. チェックリストのパース

Issue 本文からチェックリスト形式の行を抽出:

- `- [ ]` で始まる行を **未完了項目** として抽出
- `- [x]` または `- [X]` で始まる行は **完了済み** としてスキップ

各行から以下を抽出:
- **トピック名**: チェックボックスの直後のテキスト
- **フォーカス指示**: 括弧 `()` 内のテキスト（省略可）

**パース例:**
| 行 | トピック名 | フォーカス指示 |
|----|------------|----------------|
| `- [ ] Transformer` | Transformer | なし |
| `- [ ] RAG (実装パターンとベクトルDBの選択基準)` | RAG | 実装パターンとベクトルDBの選択基準 |
| `- [x] Docker` | (スキップ) | - |

### 4. 各項目の処理

調査・下書きは **Sonnet 5.5 のサブエージェント**が項目ごとに並列で行い，**メイン（Opus 5.5）**が一次情報源と突き合わせて精査してから `Notes/` に反映する．

| 担当 | モデル | 役割 |
|------|--------|------|
| 調査サブエージェント | Sonnet 5.5（`model: "sonnet"`） | WebSearch・WebFetch による調査，ノート下書き，主張と出典の対応表の作成 |
| メイン | Opus 5.5 | 既存ノート確認・モード判定，サブエージェントの起動，精査・修正，`Notes/` への反映，逆リンク，Issue 更新，コミット |

#### 4.1 既存ノートの確認とモード判定（メイン）

未完了項目のうち先頭から最大処理数までを対象にする（新規・更新どちらも処理数に数える）:

- 項目名が長い場合（括弧の外に列挙がある等）は，ノート名として自然な短い名前をここで決めておく
- `Notes/{トピック名}.md` が既に存在するか確認する
  - 存在しない場合: **新規**モード
  - 存在する場合: **更新**モード
- 表記ゆれ（大文字小文字，`.js` の有無，日本語/英語名など）で実質同じノートが既にありそうな場合は，`Notes/` のファイル一覧から候補を探し，該当すれば**更新**モードとしてそのノートを対象にする．判断がつかない場合はユーザーに確認する
- **更新**モードの項目は，既存ノートの本文を読み，frontmatter の `date` / `updated` から前回の記述時点を把握しておく

あわせて `Notes/` のファイル一覧を取得しておく（サブエージェントに渡す関連ノート候補として使う）．

#### 4.2 調査サブエージェントの起動（Sonnet 5.5）

対象項目ごとに Agent ツールでサブエージェントを1つ起動する．**すべて1つのメッセージで並列に起動する**．

- `subagent_type`: `general-purpose`
- `model`: `sonnet`
- 下書きの出力先: メインのスクラッチパッドディレクトリ配下の `research-queue/{トピック名}.md`（絶対パスで渡す）．**`Notes/` には書かせない**

プロンプトには以下をすべて含める（サブエージェントはこの会話の文脈を持たないため，必要な情報は省略しない）:

1. トピック名，フォーカス指示，今日の日付（`YYYY-MM-DD`），処理モード（新規 / 更新）
2. 下書きの出力先の絶対パス
3. 調査の観点
   - **新規**モード: 以下の4観点それぞれで WebSearch を最低1回行うこと
     1. **基本概念**: トピックの定義，歴史，背景
     2. **フォーカス内容**: フォーカス指示に沿った詳細情報（指示がある場合）
     3. **最新動向**: 最新バージョン，最近の発表，トレンド
     4. **実践例**: ユースケース，ベストプラクティス，実装例
   - **更新**モード: 既存ノートの絶対パスと前回の記述時点（`date` / `updated`）を渡し，まず既存ノートを読ませる．そのうえで以下の観点それぞれで WebSearch を最低1回行うこと
     1. **フォーカス内容**: フォーカス指示に沿った詳細情報（指示がある場合）．既存ノートで手薄な部分を補う
     2. **バージョン・リリース**: 前回記述以降の新バージョン，リリースノート，changelog
     3. **仕様変更・非推奨化**: 廃止・名称変更・破壊的変更など，既存記述が誤りになる変更
     4. **最新動向**: 前回記述以降の主要な発表やトレンド
     - 既存ノート中の事実（バージョン，日付，仕様，料金，対応状況など）は，現時点でも正しいか一次情報源で確認する
     - 既存の「参考」リンクがリンク切れ・旧情報になっていないか確認する
     - 更新方針（4.5 の「更新モードの書き方」）に従って，既存ノートを元にした更新版の全文を下書きとして出力する．既存ノートそのものは**編集しない**
4. 出典の扱い
   - 一次情報源（公式ドキュメント，公式ブログ，論文，リポジトリ）を優先し，まとめ記事経由の情報は追加検索で一次情報源を特定する
   - 数値・日付・バージョン・ベンダーの主張は，可能な限り一次情報源を WebFetch で直接読んで確認する
   - 取得できなかった出典（403 等）を，読んだかのように扱わない
   - 既存知識で補った記述は，その旨を対応表で明示する
5. 下書きの形式: 4.4 のタグ体系，4.5 のテンプレートとセクション構成（本ファイルの該当部分をそのまま貼る），Vault の文体規約（日本語，句読点は `，` `．`，本文中に `#tag` を使わない）
6. 関連ノート候補: 4.1 で取得した `Notes/` のファイル一覧．関連する既存ノートを `related` と「関連項目」に入れ，未作成のノートへのファントムリンクも積極的に使うこと．既存ノートは**編集しない**（逆リンクはメインが行う）
7. 返却フォーマット（最終メッセージとして以下を返す）:

```
## 下書き
<出力先パス>

## 主張と出典の対応表
| # | 主張（ノート中の記述の要約） | 出典URL | 出典の該当箇所（原文引用） | 取得状況 |
|---|------------------------------|---------|----------------------------|----------|
取得状況は 直接取得 / 二次情報経由 / 取得失敗 / 既存知識 のいずれか．
数値・日付・バージョン・固有の主張はすべて行を立てる．

## 情報源間の食い違い
（同じ事柄について出典ごとに値や比較対象が異なるもの）

## 既存ノートからの変更点（更新モードのみ）
| # | 種別 | 既存の記述 | 更新後の記述 | 根拠（対応表の #） |
|---|------|------------|--------------|--------------------|
種別は 修正 / 追記 / 削除 / 参考差し替え のいずれか．
更新すべき内容がなかった場合は「変更なし」と書く．

## 未確認事項
（調べきれなかった点，取得できなかった出典）
```

#### 4.3 精査と反映（メイン / Opus 5.5）

各サブエージェントの結果を受け取ったら，項目ごとに以下を行う:

1. **対応表の確認**: 各主張が引用の内容と一致しているか確認する．引用から言えないことまで書いていないか（誇張・一般化）を見る
2. **一次情報源の再取得**: 以下は自分で WebFetch して一次情報源と照合する
   - 数値（性能，価格，規模），日付，バージョン
   - ベンダー・発表元の主張
   - 取得状況が `二次情報経由` `既存知識` の主張のうち，ノートの要点に関わるもの
3. **食い違いの処理**: 情報源間で値や比較対象が異なる場合は，一次情報源の値を採用するか，ノート本文で違いを明記する．丸めて違いを見えなくしない
4. **取得失敗の出典**: 本文の根拠にしない．別の一次情報源で裏付けが取れればそれを参考に挙げる．取れなければ該当記述を削るか「未確認」と明記する．読めていない出典を読んだものとして参考に並べない
5. **規約の確認**: タグ体系，frontmatter，セクション構成，文体，関連ノートの妥当性（既存ノート名と一致しているか）
6. **更新モードの差分確認**: 既存ノートと下書きを比較し，以下を確認する
   - 変更点の表に載っていない変更（無断の書き換え・削除）がないか．あれば既存の記述に戻す
   - 削除・書き換えた既存の記述は，根拠となる一次情報源で誤り・古さが確認できているか．確認できなければ既存の記述を残す
   - 既存の `related`，関連項目のリンク，ユーザーが書き足したと思われる記述（メモ，所感，Books 由来の記述など）が失われていないか
   - 4.5 の「更新モードの書き方」（`updated`，更新履歴）に従っているか
7. 修正を反映したノートを `Notes/{トピック名}.md` に書き込む．更新モードで「変更なし」と判断した場合はノートを変更しない
8. 精査で行った修正（誤りの訂正，削除，未確認の明記など）と，更新モードでは既存ノートからの主な変更点を項目ごとに記録する（結果報告で使う）

サブエージェントが失敗した，または下書きが精査に耐えない場合は，その項目を処理失敗として扱う（Issue には残す）．

#### 4.4 タグの選定

以下のタグ体系に基づいて，親タグ+サブタグを付与:

| 親タグ | サブタグ例 |
|--------|-----------|
| `AI` | `LLM`, `ML`, `Agent`, `NLP`, `ComputerVision` |
| `Web` | `Frontend`, `Backend`, `API`, `Framework` |
| `Cloud` | `AWS`, `GCP`, `Azure`, `K8s`, `Serverless` |
| `DevOps` | `CI/CD`, `IaC`, `Monitoring` |
| `Security` | `Auth`, `Encryption`, `ZeroTrust` |
| `DB` | `SQL`, `NoSQL`, `VectorDB` |
| `Language` | `Python`, `TypeScript`, `Go`, `Rust` |
| `Tool` | `Git`, `Editor`, `CLI` |

#### 4.5 ノートの構成

下書き・最終版とも `Templates/tech-note.md` のテンプレート構造に従って日本語で書く:

```yaml
---
title: "トピック名"
date: YYYY-MM-DD
tags:
  - 親タグ
  - サブタグ
related:
  - "[[関連ノート]]"
---
```

**セクション構成:**
- **概要**: トピックの簡潔な説明（1-3文）
- **詳細**: トピックの詳細な解説．フォーカス指示がある場合はその内容を重点的に記述
- **ポイント**: 重要な点を箇条書きで整理
- **関連項目**: 関連する既存ノートへの `[[ノート名]]` リンク
- **参考**: 調査で使用した一次情報源へのリンク

**更新モードの書き方:**
- **既存構成を維持する**: セクション構成と既存の文体を保ち，全面的な書き直しはしない
- **古くなった記述は書き換える**: 誤りになった事実は修正し，必要なら「（YYYY-MM-DD 時点）」と時点を明記する
- **新情報は該当セクションに組み込む**: 末尾にまとめて足すのではなく，内容に合った位置に追記する
- **参考を更新する**: 新たに使った一次情報源を追加し，リンク切れ・旧情報のリンクは差し替える
- **frontmatter**: `date`（初回作成日）は変更せず，`updated: YYYY-MM-DD` を追加または更新する．`tags` はタグ体系に沿って必要な場合のみ見直す．既存の `related` は削除しない
- **更新履歴を残す**: 「参考」の後に `## 更新履歴` セクションを設け（なければ作成），`- YYYY-MM-DD: 変更点の要約` を1行追記する
- 更新すべき内容がなければノートを変更しない（`updated` も変えない）

#### 4.6 双方向リンクの整合性維持（メイン）

関連ノートとしてリンクした既存ノート（今回同時に作成したノートを含む）に対して，逆リンクを追加する．更新モードでは，今回新たに追加したリンクが対象:

1. リンク先ノートの `related` frontmatter に `"[[今回のトピック名]]"` を追加
2. リンク先ノートの「関連項目」セクションに `- [[今回のトピック名]]` を追加

**注意**: 既に逆リンクが存在する場合は追加しない

#### 4.7 処理完了の記録

処理が完了した項目を，モード（新規 / 更新 / 更新・変更なし）とともに内部リストに記録する．更新モードで「変更なし」と判断した項目も処理完了として扱う．

### 5. Issue の更新

すべての処理が完了したら，Issue を更新:

1. 処理完了した項目のチェックリスト行を Issue 本文から削除する
2. `gh issue edit <番号> --body "..."` で Issue 本文を更新

**重要**:
- 1項目でも処理が完了していれば，その分だけ Issue を更新する
- 処理に失敗した項目は `- [ ]` のまま残す

### 6. コミットとプッシュ

処理が1件以上完了している場合，変更をコミットしてリモートにプッシュする:

1. 新規作成・更新したノートファイルと逆リンクを追加した既存ノートファイル（`Notes/` 配下）を `git add` でステージング
2. 以下の形式でコミットメッセージを作成し `git commit` する:
   - 形式: `技術調査(YYYY/MM/DD): トピック1, トピック2, ...`
   - 更新モードの項目はトピック名の後に `(更新)` を付ける
   - 例: `技術調査(2026/02/10): Transformer, RAG(更新), Docker`
3. `git push` でリモートにプッシュ

**注意**: ノートに変更が1件もない場合（未完了のみ，または更新モードがすべて「変更なし」）はコミット・プッシュを行わない

### 7. 結果報告

処理結果をユーザーに報告:

```
## 処理結果

**新規作成**: X 件
- [[トピック1]] - フォーカス指示（あれば）
- [[トピック2]]

**更新**: Y 件
- [[トピック3]] - 主な変更点（例: v2.0 のリリースを反映，非推奨 API の記述を修正）
- [[トピック5]] - 変更なし

**処理失敗**: W 件（Issue に残した）
- トピック4 - 理由

**残り未処理**: Z 件

## 精査結果
- [[トピック1]]: 修正 N 件（例: 価格の桁を一次情報源に合わせて訂正，比較対象の違いを明記）
- [[トピック2]]: 修正なし
- 未確認のまま残した事項: （あれば）
```

## エラーハンドリング

- Issue が存在しない場合: エラーメッセージを表示して終了
- Issue にチェックリストがない場合: その旨を報告して終了
- 未完了項目がない場合: 「すべての項目が完了済みです」と報告して終了
- 個別項目の処理失敗: エラーをログに記録し，次の項目へ進む（完了分は Issue に反映）
- サブエージェントの失敗・不完全な返却: 返却フォーマットが欠けている場合は，その項目だけサブエージェントを1回だけ再起動する．それでも失敗したら処理失敗として Issue に残す（メインが代わりに調査をやり直すことはしない）
