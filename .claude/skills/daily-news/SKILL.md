# デイリーニュース作成

候補の収集は Sonnet 5.5 のサブエージェントが分野ごとに並列で行い，メインの Opus 5.5 が一次情報源と突き合わせて精査・選別し，最終的な内容に責任を持ってから `DailyNews/` に書き込みます．

## 使用方法

```
/daily-news [YYYY-MM-DD]
```

- 日付を省略した場合は今日の日付を使う

## 役割分担

| 担当 | モデル | 役割 |
|------|--------|------|
| 収集サブエージェント | Sonnet 5.5（`model: "sonnet"`） | 担当分野の候補を WebSearch・WebFetch で集め，一次情報源の URL・公開日・根拠の引用つきで候補リストを返す |
| メイン | Opus 5.5 | 日付決定，サブエージェントの起動，一次情報源の再取得による精査，選別，要約の確定，ファイル作成，コミット |

## 構成（セクション）

| セクション | 内容 | 対象期間 | 掲載数の目安 |
|------------|------|----------|--------------|
| AI / ML | AI・機械学習のニュース | 直近2日 | 5〜8件 |
| プログラミング言語・開発ツール | 監視対象の言語・エディタ・開発支援ツールのリリースと更新内容の要約 | 前回の DailyNews 以降 | 更新があったものすべて |
| データビジネス | 国内外の企業のデータビジネス．特にデータ基盤の導入・刷新による改善事例 | 直近7日 | 2〜5件 |
| 脆弱性 | 悪用確認済み・Critical の脆弱性 | 直近2日 | 3〜6件 |
| 注目論文（arXiv） | 注目論文 | 直近数日 | 3〜5本 |

## 処理手順

### 1. 日付と対象期間の決定

- `$ARGUMENTS` が指定されている場合，その値を日付（YYYY-MM-DD 形式）として使用する．指定がない場合は今日の日付を使用する
- `DailyNews/` 内で対象日付より前の最新ファイルを探し，その日付を「前回の DailyNews 日付」とする．プログラミング言語・開発ツールの対象期間は「前回の DailyNews 日付の翌日〜対象日付」とする．前回がない，または30日より前の場合は直近14日とする
- 前回の DailyNews にプログラミング言語・開発ツールのセクションがあれば，掲載済みのツールとバージョンを控えておく（重複掲載を避けるため）

### 2. 既存ファイルの確認

- `DailyNews/YYYY-MM-DD.md` が既に存在するか確認する
- 存在する場合はユーザーに上書きするか確認を取る

### 3. 収集サブエージェントの起動（Sonnet 5.5）

以下の5分野ごとに Agent ツールでサブエージェントを1つ起動する．**5つとも1つのメッセージで並列に起動する**．

| 分野 | 担当範囲 | 返す候補数の目安 |
|------|----------|------------------|
| AI / ML | AI・機械学習のニュース（モデル発表，製品，研究機関・企業の動き，資金調達，規制） | 8〜10件 |
| プログラミング言語・開発ツール | 4.の「プログラミング言語・開発ツールの収集方針」に従う | 対象期間内の更新すべて |
| データビジネス | 4.の「データビジネスの収集方針」に従う | 5〜8件 |
| 脆弱性 | 4.の「脆弱性の収集方針」に従う | 5〜8件 |
| arXiv 論文 | 4.の「論文の収集方針」に従う | 6〜8本 |

- `subagent_type`: `general-purpose`
- `model`: `sonnet`
- 候補リストの出力先: メインのスクラッチパッドディレクトリ配下の `daily-news/YYYY-MM-DD/{分野}.md`（絶対パスで渡す）．**Vault 内には書かせない**

プロンプトには以下をすべて含める（サブエージェントはこの会話の文脈を持たないため，必要な情報は省略しない）:

1. 対象日付（`YYYY-MM-DD`），担当分野，対象期間（上の「構成」の表と 1. で決めた期間を具体的な日付で書く），候補数の目安，候補リストの出力先の絶対パス
2. 担当分野の収集方針（4. の該当部分をそのまま貼る）．プログラミング言語・開発ツールでは，前回掲載済みのツールとバージョンも渡す
3. 公開日を一次情報源で確認できないもの，対象期間外のものは候補に入れない
4. 収集元: CLAUDE.md の「ニュースソース」と 4. の情報源を手がかりにする．ただし URL は**一次情報源**（公式ブログ，公式発表，プレスリリース，リリースノート，リポジトリ，セキュリティアドバイザリ，企業の技術ブログ，論文）を特定して使う．まとめ記事・ニュースアグリゲーター・報道記事しか見つからないものは，その旨を明記する
5. 確認の仕方
   - 各候補の一次情報源を WebFetch で直接読み，タイトル・公開日・バージョン・数値（性能，金額，規模，CVSS など）・主張を確認する
   - 取得できなかった出典（403 等）を，読んだかのように扱わない
   - 既存知識で補った記述は，その旨を明示する
6. Vault の文体規約: 日本語，句読点は `，` `．`，要約は1〜2文（プログラミング言語・開発ツールは主な変更点を2〜3点）
7. 禁止事項: Vault（`/Users/citrus/Hobbies/obsidian/obsidian-tech-notes`）内のファイルを一切編集・作成しない．git 操作をしない
8. 返却フォーマット（最終メッセージとして以下を返し，同じ内容を出力先にも書く）:

```
## 候補リスト（{分野}）
| # | タイトル | 一次情報源URL | 発行元 | 公開日 | 要約（日本語1〜2文） | 根拠（一次情報源の原文引用） | 取得状況 | 推薦度 |
|---|----------|---------------|--------|--------|----------------------|------------------------------|----------|--------|
取得状況は 直接取得 / 二次情報経由 / 取得失敗 / 既存知識 のいずれか．
推薦度は A（必ず載せるべき）/ B / C．
分野ごとに以下の列を追加する:
- プログラミング言語・開発ツール: ツール名 | バージョン | 区分（メジャー / マイナー / パッチ） | 主な変更点（2〜3点） | 破壊的変更・非推奨の有無
- データビジネス: 企業名 | 国内/海外 | 発表の種類（企業自身の発表 / ベンダーの導入事例 / 報道） | 導入・刷新した基盤 | 課題 | 効果（数値は出典どおり）
- 脆弱性: CVE ID | 対象製品・バージョン | CVSS（出典） | 悪用状況 | 修正版・対処
- 論文: 著者（筆頭著者 et al.）| arXiv ID | 投稿日 | コード公開の有無

## 更新なし（プログラミング言語・開発ツールのみ）
（監視対象のうち，対象期間内に更新がなかったもの）

## 情報源間の食い違い
（同じ事柄について出典ごとに値や日付が異なるもの）

## 未確認事項
（一次情報源を特定・取得できなかった候補とその理由）
```

### 4. 分野別の収集方針

#### AI / ML

- CLAUDE.md の「選別基準」に従う
- モデル発表，製品リリース，研究機関・企業の大きな動き，資金調達，規制を対象とする

#### プログラミング言語・開発ツールの収集方針

監視対象ごとに，対象期間内のリリースを一次情報源（公式のリリースノート・changelog・GitHub Releases・公式ブログ）で確認する．

| 区分 | 監視対象 | 一次情報源の例 |
|------|----------|----------------|
| 言語 | Python | https://www.python.org/downloads/ ，https://blog.python.org ，PEP（https://peps.python.org） |
| 言語 | Rust | https://blog.rust-lang.org ，https://github.com/rust-lang/rust/releases |
| 言語 | Julia | https://julialang.org/blog/ ，https://github.com/JuliaLang/julia/releases |
| エディタ | VS Code | https://code.visualstudio.com/updates |
| エディタ | Zed | https://zed.dev/releases ，https://zed.dev/blog |
| エディタ | Helix | https://github.com/helix-editor/helix/releases |
| 開発支援ツール | Claude Code | https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md |
| 開発支援ツール | その他の AI コーディングツール（Codex CLI，Gemini CLI，Cursor，GitHub Copilot 等） | 各公式の changelog・リリースノート |

- 言語は処理系本体の正式リリース（RC・ベータは重要なものだけ），大きな言語仕様の決定（PEP の採択，Rust の Edition 等）を対象とする．言語周辺の主要ツール（Python の uv / ruff，Rust の cargo 等）の大きなリリースも候補にしてよい
- その他の AI コーディングツールは，大きな機能追加・料金変更などがあった場合だけ候補にする
- 頻繁にリリースされるツール（Claude Code，Zed 等）は，対象期間内の複数リリースを1行にまとめ，「v1.2.3〜v1.2.8」のように範囲で書く．細かい修正は省き，ユーザーに影響する変更（新機能，挙動の変更，破壊的変更，非推奨化）を拾う
- 前回掲載済みのバージョンは候補にしない
- 対象期間内に更新がなかった監視対象は「更新なし」に列挙する

#### データビジネスの収集方針

- **対象**: 国内外の企業によるデータ活用・データビジネスの動き．特に**新しいデータ基盤を導入・刷新して改善した事例**を優先する
  - 例: データウェアハウス・レイクハウスへの移行（Snowflake，Databricks，BigQuery，Apache Iceberg 等），データ基盤の内製化・統合，データメッシュ・データカタログの導入，リアルタイム分析基盤の構築，データ活用による事業改善
  - データ関連企業の買収・提携・資金調達，データ製品の提供開始も対象とする
- **情報源**（一次情報源として URL に使う）:
  - 企業自身の技術ブログ・プレスリリース（例: メルカリ，LINEヤフー，ZOZO，リクルート，Netflix，Uber，Airbnb 等のエンジニアリングブログ）
  - データ基盤ベンダーの導入事例・発表（Snowflake，Databricks，Google Cloud，AWS，Microsoft 等）
  - 発見の手がかり: Publickey，ITmedia，日経クロステック，InfoQ 等の報道（URL には使わず一次情報源をたどる）
- **選別基準**（上ほど優先）:
  1. 課題・導入した基盤・効果が具体的に書かれた事例（移行前後の構成，数値の改善）
  2. 企業自身が発表した事例（ベンダーの導入事例より優先）
  3. 国内企業の事例を最低1件は含めるよう探す
- ベンダーの導入事例の効果の数値はベンダーの主張として扱い，その旨を区別する

#### 脆弱性の収集方針

- **情報源**（一次情報源として URL に使う）:
  - CISA Known Exploited Vulnerabilities Catalog（https://www.cisa.gov/known-exploited-vulnerabilities-catalog）
  - NVD（https://nvd.nist.gov）
  - JVN（https://jvn.jp）/ JPCERT/CC（https://www.jpcert.or.jp）/ IPA（https://www.ipa.go.jp/security/）
  - GitHub Advisory Database（https://github.com/advisories）
  - ベンダーのセキュリティアドバイザリ（Microsoft MSRC，Apple，Google Chrome Releases，Cisco，Fortinet，Ivanti，Linux ディストリビューション，各 OSS プロジェクトのリリースノート等）
- **選別基準**（上ほど優先）:
  1. 実際の悪用が確認されているもの（CISA KEV への追加，ベンダーが "exploited in the wild" と明言）
  2. CVSS 9.0 以上（Critical）の脆弱性
  3. 広く使われる製品（OS，ブラウザ，VPN・ネットワーク機器，クラウド，コンテナ，主要 OSS ライブラリ）
  4. 開発者が日常的に使うツール・AI 関連ツール（パッケージマネージャ，CI/CD，エディタ，LLM 実行環境，MCP サーバー等）やサプライチェーン攻撃
- CVSS は出典（NVD / ベンダー / CNA）を明記する．NVD とベンダーで値が異なる場合は両方書く
- 製品・影響バージョン・修正バージョンはベンダーのアドバイザリで確認する

#### 論文の収集方針

- arXiv の最新論文から注目論文を候補にする
- 対象カテゴリ: `cs.AI`, `cs.CL`, `cs.CV`, `cs.LG`, `cs.MA` 等
- 直近数日以内に投稿・更新された論文を対象とする
- 選別基準: 新手法の提案，SOTA 更新，実用的応用（コード公開あり優先），SNS等で話題の研究，著名な研究機関・企業からの発表
- arXiv の abs ページで，タイトル・著者・投稿日・アブストラクトを確認する

### 5. 精査と選別（メイン / Opus 5.5）

5つのサブエージェントの結果が揃ったら，以下を行う．**最終的な内容の正しさにはメインが責任を持つ**:

1. **重複の排除**: 分野をまたいで同じ話題が挙がっていれば，最も適したセクションに1件だけ残す（例: Claude Code の新機能は AI / ML ではなくプログラミング言語・開発ツールに入れる．データ基盤ベンダーの AI 機能発表はデータビジネスに入れる）
2. **選別**: 推薦度と選別基準をもとに，掲載する項目を決める（掲載数は「構成」の表の目安に従う）
3. **一次情報源の再取得**: 掲載する項目は**すべて**自分で WebFetch して以下を照合する
   - URL が一次情報源であること（まとめ記事・アグリゲーターでないこと）
   - 公開日が対象期間内であること
   - タイトル，数値（性能，金額，規模），ベンダー・発表元の主張が要約と一致していること
   - プログラミング言語・開発ツール: バージョン番号，リリース日，主な変更点がリリースノートに書かれていること．前回掲載済みでないこと
   - データビジネス: 企業名，導入した基盤，効果の数値とその主張元（企業自身かベンダーか）
   - 脆弱性: CVE ID，対象製品・バージョン，CVSS とその出典，悪用状況，修正版
   - 論文: タイトル，筆頭著者，投稿日
4. **要約の確認**: 引用から言えないことまで書いていないか（誇張・一般化・推測）を見て，必要なら書き直す
5. **食い違いの処理**: 情報源間で値が異なる場合は一次情報源の値を採用するか，要約中で違いを明記する
6. **取得失敗・二次情報のみの項目**: 一次情報源で裏付けが取れないものは掲載しない
7. 精査で行った修正（訂正，差し替え，不採用にした項目と理由）を記録する（結果報告で使う）

サブエージェントが失敗した，または返却フォーマットが欠けている場合は，その分野だけサブエージェントを1回だけ再起動する．それでも失敗したら，その分野は空として扱い，結果報告に含める．

### 6. ノートの作成

- `Templates/daily-news.md` のテンプレート構造に従って記述する
- 各記事・論文は日本語で1行に要約する
- frontmatter の `date` に対象日付を設定する
- 項目がないセクションのテーブルにはデータ行を含めない
- **URL は必ず一次情報源を使用する**．ソース列には一次情報源の発行元を記載する
- プログラミング言語・開発ツールセクションの書き方:
  - 「ツール」列: ツール名．「バージョン」列: `[v1.2.3](リリースノートURL)` の形式（範囲の場合は `v1.2.3〜v1.2.8` とし，最新版のリリースノートにリンク）
  - 「主な変更点」列: ユーザーに影響する変更を2〜3点，`．` 区切りで書く．破壊的変更・非推奨化があれば先頭に「【破壊的変更】」と書く
  - 監視対象のうち更新がなかったものは，表の下に「更新なし: Julia，Helix」のように1行で書く
- データビジネスセクションの書き方:
  - 「企業」列: 企業名（国内企業は日本語名）
  - 「要約」列: 課題，導入・刷新した基盤，効果を1〜2文で書く．ベンダーの導入事例の数値は「（ベンダー発表）」と付ける
- 論文の著者欄は「筆頭著者 et al.」の形式で記載する
- 脆弱性セクションの書き方:
  - 「脆弱性」列: `[CVE-YYYY-NNNNN](アドバイザリURL)` の形式．複数 CVE をまとめる場合は代表の CVE をリンクし，残りは要約に書く
  - 「深刻度」列: `CVSS 9.8（NVD）` のように値と出典を書く．悪用が確認されていれば `／悪用確認` を付ける
  - 「要約」列: 何が起きるか（RCE，認証回避など），影響バージョン，修正版・対処を1〜2文で書く

### 7. ファイルの保存

- `DailyNews/YYYY-MM-DD.md` として保存する

### 8. コミットとプッシュ

作成したデイリーニュースファイルをコミットしてリモートにプッシュする:

1. 対象ファイル（`DailyNews/YYYY-MM-DD.md`）を `git add` でステージング
2. 以下の形式でコミットメッセージを作成し `git commit` する:
   - 形式: `デイリーニュース(YYYY/MM/DD): 主要トピック1, トピック2, ...等`
   - 例: `デイリーニュース(2026/02/10): OpenAI Frontier, Big Tech AI投資$650B, Agent Trace等`
   - AI/ML カテゴリから主要な2〜3件をピックアップしてコミットメッセージに含める
3. `git push` でリモートにプッシュ

### 9. 結果の報告

```
## デイリーニュース YYYY-MM-DD

掲載: AI/ML N 件，言語・開発ツール N 件，データビジネス N 件，脆弱性 N 件，論文 N 本

## 精査結果
- 修正: （例: 金額を一次情報源に合わせて訂正，URL をまとめ記事から公式ブログに差し替え）
- 不採用: （例: 公開日が対象期間外，一次情報源を特定できない）
- 失敗した分野: （あれば）
```
