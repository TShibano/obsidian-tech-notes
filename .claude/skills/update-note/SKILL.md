# ノート最新化

Vault ルートの `update-queue.toml` に書かれたノートを読み込み，当日時点の最新情報で更新します．
`update-queue.toml` は定期的に最新化したいノートの一覧として扱い，**スキルからは一切編集しない**（項目の追加・削除はユーザーが行う）．
調査と更新版の下書きは Sonnet 5.5 のサブエージェントがノートごとに並列で行い，メインの Opus 5.5 が一次情報源・既存ノートと突き合わせて精査してから反映します．

## 使用方法

```
/update-note
```

- 引数はない．`update-queue.toml` に書かれたノートを**毎回すべて**処理する

## キューファイルの書式

`update-queue.toml`（Vault ルート）:

```toml
[[notes]]
name = "Claude Model"            # 必須: Notes/ のファイル名（拡張子なし）
focus = "最新モデルと料金の反映"   # 任意: 重点的に調べる観点

[[notes]]
name = "llama.cpp"
```

- `focus` がなければ「最新バージョン・仕様変更・非推奨化・新しい動向」を幅広く確認する

## 役割分担

| 担当 | モデル | 役割 |
|------|--------|------|
| 調査サブエージェント | Sonnet 5.5（`model: "sonnet"`） | 既存ノートの読解，WebSearch・WebFetch による調査，更新版の下書き，変更点と出典の対応表の作成 |
| メイン | Opus 5.5 | キューの読み取り，サブエージェントの起動，精査・修正，`Notes/` への反映，逆リンク，コミット |

## 処理手順

### 1. キューの読み取り（メイン）

1. `update-queue.toml` を読み取る．ファイルがない，または `[[notes]]` が空なら，書式例を示して終了する
2. 各項目の `Notes/{name}.md` が存在するか確認する．存在しない項目はスキップして報告に含める（新規作成は `/tech-note` の役割なので行わない）
3. 存在する項目を**すべて**対象にする（件数の上限や，前回の更新日による除外は行わない）
4. 各対象ノートの frontmatter の `date` / `updated` から前回の記述時点を控えておく
5. `Notes/` のファイル一覧を取得しておく（サブエージェントに渡す関連ノート候補として使う）

### 2. 調査サブエージェントの起動（Sonnet 5.5）

対象ノートごとに Agent ツールでサブエージェントを1つ起動する．**1つのメッセージで並列に起動する**．

- 対象が多い場合は **5件ずつのバッチ**に分け，前のバッチの精査（3.）と反映が終わってから次のバッチを起動する（同時に扱う下書きを減らし，精査の質を保つため）
- `subagent_type`: `general-purpose`
- `model`: `sonnet`
- 下書きの出力先: メインのスクラッチパッドディレクトリ配下の `update-note/{ノート名}.md`（絶対パスで渡す）．**`Notes/` には書かせない**

プロンプトには以下をすべて含める（サブエージェントはこの会話の文脈を持たないため，必要な情報は省略しない）:

1. ノート名，`focus`（あれば），今日の日付（`YYYY-MM-DD`），前回の記述時点（`date` / `updated`）
2. 既存ノートの絶対パスと，下書きの出力先の絶対パス
3. 作業内容
   - まず既存ノートを全文読み，記述されている事実（バージョン，日付，仕様，料金，対応状況など）を洗い出す
   - 洗い出した事実が現時点でも正しいか，一次情報源で確認する
   - 既存の「参考」リンクがリンク切れ・旧情報になっていないか確認する
4. 調査の観点（以下それぞれで WebSearch を最低1回行うこと）
   1. **フォーカス内容**: `focus` に指定された観点（指定がある場合）
   2. **バージョン・リリース**: 前回記述以降の新バージョン，リリースノート，changelog
   3. **仕様変更・非推奨化**: 廃止・名称変更・破壊的変更など，既存記述が誤りになる変更
   4. **最新動向**: 前回記述以降の主要な発表やトレンド
5. 出典の扱い
   - 一次情報源（公式ドキュメント，公式ブログ，リリースノート，論文，リポジトリ）を優先し，まとめ記事経由の情報は追加検索で一次情報源を特定する
   - 数値・日付・バージョン・ベンダーの主張は，可能な限り一次情報源を WebFetch で直接読んで確認する
   - 取得できなかった出典（403 等）を，読んだかのように扱わない
   - 確証の取れない情報は反映しない
6. 下書きの書き方: 4. の「更新の書き方」をそのまま貼る．Vault の文体規約（日本語，句読点は `，` `．`，本文中に `#tag` を使わない）とタグ体系（5. の表）も貼る
7. 関連ノート候補: 1. で取得した `Notes/` のファイル一覧．新たに関連する既存ノートがあれば `related` と「関連項目」に追加してよい．既存ノートは**一切編集しない**（逆リンクはメインが行う）
8. 更新すべき内容がなければ下書きを書かず，返却で「変更なし」と報告すること
9. 返却フォーマット（最終メッセージとして以下を返す）:

```
## 下書き
<出力先パス>（変更なしの場合は「変更なし」）

## 既存ノートからの変更点
| # | 種別 | 既存の記述 | 更新後の記述 | 根拠（対応表の #） |
|---|------|------------|--------------|--------------------|
種別は 修正 / 追記 / 削除 / 参考差し替え / リンク追加 のいずれか．

## 主張と出典の対応表
| # | 主張（変更点の根拠となる記述の要約） | 出典URL | 出典の該当箇所（原文引用） | 取得状況 |
|---|--------------------------------------|---------|----------------------------|----------|
取得状況は 直接取得 / 二次情報経由 / 取得失敗 / 既存知識 のいずれか．
数値・日付・バージョン・固有の主張はすべて行を立てる．

## 情報源間の食い違い
（同じ事柄について出典ごとに値や比較対象が異なるもの）

## 未確認事項
（調べきれなかった点，取得できなかった出典，現時点の正しさを確認できなかった既存記述）
```

### 3. 精査と反映（メイン / Opus 5.5）

各サブエージェントの結果を受け取ったら，ノートごとに以下を行う:

1. **差分の確認**: 既存ノートと下書きを比較する
   - 変更点の表に載っていない変更（無断の書き換え・削除）がないか．あれば既存の記述に戻す
   - 削除・書き換えた既存の記述は，根拠となる一次情報源で誤り・古さが確認できているか．確認できなければ既存の記述を残す
   - 既存の `related`，関連項目のリンク，ユーザーが書き足したと思われる記述（メモ，所感，Books 由来の記述など）が失われていないか
2. **対応表の確認**: 各主張が引用の内容と一致しているか確認する．引用から言えないことまで書いていないか（誇張・一般化）を見る
3. **一次情報源の再取得**: 以下は自分で WebFetch して一次情報源と照合する
   - 新たに書き込まれた数値（性能，価格，規模），日付，バージョン
   - ベンダー・発表元の主張
   - 取得状況が `二次情報経由` `既存知識` の主張のうち，ノートの要点に関わるもの
4. **食い違いの処理**: 情報源間で値や比較対象が異なる場合は，一次情報源の値を採用するか，ノート本文で違いを明記する．丸めて違いを見えなくしない
5. **取得失敗の出典**: 本文の根拠にしない．別の一次情報源で裏付けが取れればそれを参考に挙げる．取れなければその変更は反映しない．読めていない出典を読んだものとして参考に並べない
6. **規約の確認**: 4. の「更新の書き方」，タグ体系，文体，追加された関連ノート名が既存ノート名と一致しているか
7. 修正を反映したノートを `Notes/{ノート名}.md` に書き込む．「変更なし」の場合，または精査の結果反映できる変更が残らなかった場合はノートを変更しない
8. 精査で行った修正（誤りの訂正，差し戻し，未反映にした変更など）と，既存ノートからの主な変更点をノートごとに記録する（結果報告で使う）

サブエージェントが失敗した，または返却フォーマットが欠けている場合は，そのノートだけサブエージェントを1回だけ再起動する．それでも失敗したら処理失敗として報告する（メインが代わりに調査をやり直すことはしない）．1件が失敗しても残りの処理は続ける．

### 4. 更新の書き方

- **既存構成を維持する**: セクション構成（概要 / 詳細 / ポイント / 関連項目 / 参考）と既存の文体を保ち，全面的な書き直しはしない
- **古くなった記述は書き換える**: 誤りになった事実は修正し，必要なら「（YYYY-MM-DD 時点）」と時点を明記する
- **新情報は該当セクションに組み込む**: 末尾にまとめて足すのではなく，内容に合った位置に追記する
- **参考を更新する**: 新たに使った一次情報源を「参考」に追加する．リンク切れ・旧情報のリンクは差し替える
- **frontmatter**: `date`（初回作成日）は変更せず，`updated: YYYY-MM-DD` を追加または更新する．`tags` はタグ体系に沿って必要な場合のみ見直す．既存の `related` は削除しない
- **更新履歴を残す**: 「参考」の後に `## 更新履歴` セクションを設け（なければ作成），`- YYYY-MM-DD: 変更点の要約` を1行追記する
- 更新すべき内容がなければノートを変更しない（`updated` も変えない）

### 5. タグ体系

| 親タグ | サブタグ例 |
|--------|-----------|
| `AI` | `LLM`, `ML`, `Agent`, `NLP`, `ComputerVision` |
| `Web` | `Frontend`, `Backend`, `API`, `Framework` |
| `Cloud` | `AWS`, `GCP`, `Azure`, `K8s`, `Serverless` |
| `DevOps` | `CI/CD`, `IaC`, `Monitoring` |
| `Security` | `Auth`, `Encryption`, `ZeroTrust` |
| `DB` | `SQL`, `NoSQL`, `VectorDB` |
| `Language` | `Python`, `TypeScript`, `Go`, `Rust` |
| `Tool` | `Git`, `Editor`, `CLI` |

### 6. 双方向リンクの整合性維持（メイン）

更新で新たに `[[ノート名]]` リンクを追加した場合，逆リンクを追加する:

1. リンク先ノートの `related` frontmatter に `"[[今回のノート名]]"` を追加
2. リンク先ノートの「関連項目」セクションに `- [[今回のノート名]]` を追加

既に逆リンクが存在する場合は追加しない．並列で更新した複数のノートが同じノートに逆リンクを追加する場合は，まとめて1回で編集する．

### 7. キューファイルは編集しない

- 処理済み・スキップ・失敗のいずれの項目も `update-queue.toml` から削除しない．コメントや記載順も含めて一切書き換えない

### 8. 結果の報告

```
## ノート最新化 結果

| ノート | 結果 | 主な変更点 |
|--------|------|-----------|
| [[Claude Model]] | ✅ 更新 | Opus 5.5 を追加，料金表を更新 |
| [[llama.cpp]] | ➖ 変更なし | - |
| [[Foo]] | ⚠️ スキップ | Notes/Foo.md が存在しない |
| [[Bar]] | ❌ 失敗 | サブエージェントが2回失敗 |

対象: N 件（更新 A / 変更なし B / スキップ C / 失敗 D）

## 精査結果
- [[Claude Model]]: 修正 N 件（例: 価格の桁を一次情報源に合わせて訂正，根拠のない削除を差し戻し）
- 未確認のまま残した事項: （あれば）
```

### 9. コミットとプッシュ

1. 更新したノート，逆リンクを追加したノートを `git add` でステージング（`update-queue.toml` は含めない）
2. 以下の形式でコミットメッセージを作成し `git commit` する:
   - 形式: `ノート更新(YYYY/MM/DD): ノート名1, ノート名2, ...`
   - 例: `ノート更新(2026/11/09): Claude Model, llama.cpp`
3. `git push` でリモートにプッシュ
4. 更新したノートが1件もない場合はコミットしない
